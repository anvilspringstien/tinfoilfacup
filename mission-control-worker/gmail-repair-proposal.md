# Phase 2C.2 and 2C.3 Gmail reliability

The source review and approved scope below describe the recovered Worker before the repair. The implementation is covered by the [Mission Control regression suite](worker.test.mjs) in the baseline and isolated environments.

## Recovered behaviour

| Path | Observed in the source |
| --- | --- |
| Mission Control session | Google sign-in requests `openid email`. The resulting signed dashboard cookie lasts one hour. Gmail API routes return `401 sign_in_required` when this session is missing or invalid. |
| Gmail permission | A separately requested `gmail.readonly` grant uses online access. Its encrypted cookie uses the provider's expiry minus a 45-second buffer, capped at 3,500 seconds, normally bounded by the dashboard session, with a 30-second floor. Every Gmail route also requires the valid dashboard session. The grant is bound to that session's account and the Worker does not store a refresh token. A missing or locally expired grant results in `connected: false` on status, or `401 gmail_not_connected` on data routes. |
| Early provider expiry | The status route checks the local grant cookie only. If Google rejects a still-present grant, the outreach route wraps provider HTTP 401 as a 502 and drafts return a generic unavailable response. The browser currently labels every outreach HTTP 401 as Gmail permission expiry, including Mission Control sign-in expiry. |
| Disconnect | The browser sends a same-origin POST with `X-TFFAC-Action: disconnect`. The Worker requires a current dashboard session, the exact `Origin` header and the expected action header. A successful response clears the Gmail cookie for that browser and leaves the dashboard session alone. The browser currently collapses failures to “Disconnect failed”. The source and mock results establish what the route expects, while the deployed browser failure remains unconfirmed. |
| Count retention | A refresh clears the displayed current count and records before scanning. A status failure, missing grant, scan failure, disconnect or reload can remove the count from view. There is no saved last-successful aggregate. The browser already rejects failed pages, repeated tokens, a page limit that leaves more data, and a mismatch between accepted rows and returned records. Unparseable potentially eligible results and missing bodies can still coexist with a displayed current count. Draft availability is a separately paginated value. |

## Proposed scope

1. **Separate the two reconnection paths.** Give the browser stable, non-sensitive response codes for sign-in required, Gmail connect required, revoked or expired provider grant, and unavailable data. Prompt for Mission Control sign-in when the dashboard session has expired. Offer **Connect Gmail** while the dashboard session is valid. Clear an invalid local Gmail grant when the provider confirms expiry or revocation. Report quota, network, generic permission and upstream errors as their own states. Retain the existing read-only scope and online consent.
2. **Make Disconnect observable and reliable.** Keep exact-origin and action-header checks. Return a distinct sign-in-required response for a valid same-origin request with an expired session, and require explicit acknowledgement that the local cookie was cleared before showing **Disconnected**. Preserve a last-successful count as stale after disconnect. Ignore results from an older refresh when a disconnect or reconnection changes the current grant. Check the actual request from the delegated browser click in the isolated fixture, including its headers, credentials, response and subsequent status. Local disconnect clears this browser's grant. Provider-wide revocation is outside scope.
3. **Retain the last successful aggregate.** Persist the count and its completion timestamp in a versioned, origin-local browser record. Keep mailbox tokens, message bodies, addresses and draft data out of that record. Show the last count with its timestamp and a stale warning during denied access, incomplete scans, offline use and after reconnect until a new complete scan succeeds. Include it in the existing local clear-data flow.
4. **Publish only complete counts.** Stage scan results until both query families finish, all pages are accounted for and audit rows reconcile. Keep excluded replies separate from potentially eligible results with missing bodies, rejected IDs or unresolved club identity. Any incomplete or unresolved scan should surface its status and retain the last successful value. With no successful scan, show **Unknown**. A complete scan with no eligible introductions can correctly show zero. Draft availability should have its own timestamp and completeness state and must not determine the outreach count.

Extend the mocked regressions for session expiry, local grant expiry, a provider 401 during a valid dashboard session, permission or quota errors, the delegated Disconnect sequence, and in-flight refresh ordering. Cover a complete zero, an incomplete first scan, success followed by an incomplete scan, a partial draft listing, persistence across reload, and clear-data reset. Review the UI copy and result states in the isolated fixture before considering any hosted test.

## Implementation notes

- The delegated Disconnect click uses a same-origin POST with a request-specific same-origin referrer policy. The Worker continues to require its exact Origin, the action header and a valid Mission Control session. The panel confirms both the POST acknowledgement and the subsequent absence of a Gmail grant. Local disconnect does not revoke Google's grant outside that browser.
- The saved record contains a version, unique-club count and UTC completion time. Browser storage is origin-local. Gmail access errors and interrupted or unresolved scans leave the record intact. The draft listing has its own completion status and timestamp.
- Aborting an older request and checking the owning operation before updating the UI or storage prevents late same-page replies from replacing a newer result. Connection status reflects the latest check. The app does not poll Google in the background. A Gmail listing is paginated rather than an atomic mailbox snapshot.
- The two automated fixtures execute the real delegated handler with synthetic browser events and mocked providers. They do not exercise real Google consent, the hosted Cloudflare Worker, a real mailbox or cross-tab cookie timing.
- A local Chromium smoke test at the isolated origin used intercepted requests, synthetic authentication and mocked Gmail responses. On the candidate, the browser sent the exact Origin, the Worker cleared the Gmail cookie, the subsequent status check confirmed disconnect, and reload showed the retained count as stale. The dashboard session cookie remained present. The recovered build also accepted its POST in that Chromium session, so the reported live failure was not reproduced.

See the [Fetch Origin-header algorithm](https://fetch.spec.whatwg.org/#origin-header) and [Gmail API error handling](https://developers.google.com/workspace/gmail/api/guides/handle-errors).
